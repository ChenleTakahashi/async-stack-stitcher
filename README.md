# async-stack-stitcher

Correlates rejected promise traces across async boundaries by matching reject point identifiers embedded in error messages.

## Usage

```js
import { Stitcher, buildRejectMarker } from 'async-stack-stitcher';

const stitcher = new Stitcher({ maxGroups: 1000 });

const id = 'a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4'; // 32 hex chars
const error = new Error(buildRejectMarker(id, 'database connection failed'));

stitcher.recordRejection(id, error);

// Later, when a correlated rejection surfaces:
const entries = stitcher.correlate(error);
if (entries) {
  console.log(`Found ${entries.length} correlated rejection(s)`);
}
```

## Why

When promises reject across async boundaries (e.g., a worker thread, a microtask queue, or a chained `.catch()`), the original stack trace is often lost or truncated. This library provides a lightweight way to correlate rejections by embedding a unique identifier in the error message at the reject point, then matching that identifier when the error surfaces elsewhere.

The trade-off: this requires errors to carry the marker in their message string. It is not transparent to existing error handling. If your errors are generated by code you do not control, you cannot use this approach without wrapping them.

## Edge Cases

- The marker format is `[reject:<32-hex-chars>] <message>`. Leading whitespace before the marker is tolerated; any deviation (wrong length, non-hex characters, missing brackets) means the error will not be recognized.
- `correlate` returns `null` (not an empty array) when the error has no marker or the id is unknown. Check the return value before iterating.
- With `maxGroups` set, the oldest group is evicted in insertion order when capacity is exceeded. Set `maxGroups: 0` for unlimited storage.

## Performance

The window keeps a bounded buffer, so `push` is constant time and memory does not
grow with the length of the stream. `peak` and `trough` are linear in the window
size, which is the trade that keeps `push` cheap.

## Design notes

The window stores values eagerly rather than keeping running aggregates. Running
sums drift with floating point over long streams, and recomputing from a small
buffer is cheap enough that the drift is not worth the speed.
